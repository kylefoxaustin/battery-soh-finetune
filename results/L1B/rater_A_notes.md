# L1b rater A notes

Rater A, study L1b, branch `l1b-rater-a`. Fresh-context language-model session (D-3). Every event is SOURCED; every
`class` and `stack` value is a DERIVED judgement. No dollar figures.

## 1. Conventions (written and committed before any change history is read)

### 1.1 Event definition and counting

- **Event** (L1 §2): a dated adoption, amendment, revision, new edition or entry-into-force of a listed instrument that
  changes, for the instrument's domain ECU, at least one of (a) data it must produce, store, sign or transmit; (b)
  functions it must host; (c) software-lifecycle process obligations (software-update management, cybersecurity
  management, type approval of software versions).
- **Domain ECUs.** S: seat adjustment, seat heating, occupancy classification, seat-belt reminder (SBR), belts with
  pretensioner / load-limiter control, head restraints (active / adjusting), child-restraint interfaces (e.g. ISOFIX
  presence detection, airbag deactivation linked to CRS). L: lamp control units; ADB, AFS and headlamp-levelling
  controllers; light-signalling functions (stop lamps, emergency stop signal, DRL, direction indicators incl. hazard,
  cornering lamps, etc.) and the body-controller functions that drive them.
- **Where I draw the "(b) functions" line.** A requirement counts as a function the ECU must host when it changes
  the **control or monitoring logic** that an electronic controller executes: switching / activation and
  deactivation conditions (automatic switching, ESS activation, DRL / position-lamp interplay, signal priorities,
  flashing rates or sequences generated by the controller), adaptive behaviour (ADB / AFS / levelling modes and their
  inputs), failure detection with tell-tale or warning, reminders and warnings (SBR logic, warning thresholds and
  timing), variable-intensity control, and signals the controller must send or receive on a bus. For S, the same:
  SBR logic and warnings, occupant detection / classification and suppression logic, active-restraint control.
- **Not an event:** changes to photometry, colour, geometry of visibility, mounting position, dimensions, light-source
  categories and their electrical / dimensional data, materials, strength, crash or sled test procedures,
  marking and approval-mark layout, administrative / communication-form changes, transitional provisions only,
  corrigenda, editorial changes, or a new edition whose content I cannot connect to (a)–(c). A scope extension
  (new vehicle categories) is an event only if the extended scope brings an (a)–(c) obligation with it.
- **One act, one event.** The act is the document (series of amendments, supplement, amendment, revision / new
  edition, final rule, delegated or implementing act). Adoption and entry into force are one event with two dates.
  A single UN document that is formally both "Supplement x to the nn series" and "Supplement y to the mm series" is one
  event (one document); its `act_id` names the highest series and the note names the others. Separate documents
  adopted at the same session for parallel series are separate acts and separate events, each only if it meets the
  definition.
- **Never twice, within a domain (L1b §1).** If one act amends two listed instruments of the same domain, it is
  counted once, under the instrument that comes first in `L1B_instruments.md`, and noted under the other. An act that
  reaches both the S and the L ECU (e.g. one delegated act under 2019/2144) is one event of each domain, once under
  L10 and once under S13.
- **EU base acts (L10, L11, S13).** Every delegated or implementing act adopted under the base act, and every act
  amending the base act's annexes, is a candidate event of it; I read each (not only S1's titles) and keep those
  meeting the definition for the domain. Amendments that only update the list of UN regulations (series numbers) are
  counted under the EU base act only if the act itself imposes a new (a)–(c) obligation for the domain ECU (e.g. by
  making a newer UN series with a new control function mandatory with application dates); the UN amendment itself
  is the event of the UN instrument. These are different acts, so both can be events.
- **FMVSS.** Each Federal Register final rule (and response to petitions that changes requirements) that amends the
  listed section in the window. Proposed rules (NPRMs) are not events. Interim final rules are events.
- **Standards.** Each new edition / revision published in the window.

### 1.2 Classes (L1 §2)

- `software-only`: the change is in logic, thresholds, timing, modes or signals an already-fielded controller could
  implement by software update, with no new interface, no new sensor, no new cryptographic hardware, and no stated
  re-approval obligation for types already approved.
- `memory-or-crypto`: materially more storage, a secure element / HSM capability, or a new communication stack.
- `hardware-or-recert`: a new interface, sensor (e.g. ambient-light, camera, occupancy sensor), actuator or compute
  class; or it re-opens type approval. **Re-opens type approval** I apply literally: the act states that already
  approved types must be re-approved or must newly comply by a stated date (typically a new series of amendments
  whose transitional provisions let Contracting Parties refuse first national registration of vehicles not approved
  to it, or an FMVSS / EU phase-in applying to all new vehicles from a date). A supplement that applies only to new
  approvals, or is optional, does not re-open type approval.
- `cannot judge`: the text or summary read does not allow a reading (always so for events admitted under `partial`
  access unless the catalogue abstract allows more).
- When several consequences apply, the most demanding stated or clearly implied one wins
  (`software-only` < `memory-or-crypto` < `hardware-or-recert`).

### 1.3 Access states (L-3) and the partial-access rule

- `full`: I read the body's own change history (list of editions / amendments with dates) **and** the text or the
  body's own summary of each change in the window.
- `partial`: I read edition / amendment identifiers and dates from the body's own catalogue, metadata or notice pages,
  but not what changed (for some or all of them).
- `none`: no body-published history reachable by an allowed route; blocked routes (403, captcha, verification
  step, login, paywall) are recorded in `sources_tried` and never bypassed.
- **Under `partial`:** a new edition / amendment is an event only when the body's own catalogue entry (title,
  abstract, amendment title) shows its subject is data, telemetry, communication protocol, cybersecurity, software
  update or monitoring; then `class = cannot judge` (unless the abstract allows more) and `confidence = low`.
  Otherwise it is logged in §3 below as `unreadable edition` and not counted. Same rule in both domains.
- If I have the full history list but could read the content of only some amendments, the instrument is `partial`,
  and the unread amendments fall under the partial rule.
- Search-engine listings may appear in `sources_tried` and may locate a document; they never source an event.

### 1.4 `act_id` forms (L-4)

- EU act: CELEX, e.g. `32025R1122`; adoption date = the date printed on the act.
- UN regulation: `R48-06` (series), `R48-06-S12` (supplement 12 to the 06 series), `R48-06-A1`-style only if the
  document is titled as an amendment rather than a supplement; adoption date = WP.29 vote date; if only OJ / entry
  into force date found, that date with note `EIF date`. Original adoption of a new regulation: `R148-00`.
- UN GTR: `GTRnn`, `GTRnn-A1`.
- FMVSS: Federal Register citation of the final rule, e.g. `89 FR 100660`; adoption date = FR publication date;
  application date = compliance date where stated.
- Standard: identifier with edition date, `SAE J3069_201606`, `IEC 60809:2021`, `GB 4785-2019`; adoption date =
  publication date.
- Dates are written YYYY-MM-DD; `application_date` blank if the same as adoption or unknown (stated in note).

### 1.5 Window

Adoption date (standard: publication date) from 2016-01-01 to 2026-12-31 inclusive. An act adopted before 2016 but
entering into force inside the window is **not** an event. An act adopted inside the window with later application
is included with both dates.

### 1.6 `stack` (L1b §3)

- `yes` only when the act names, for the domain's ECU, at least one of: a cryptographic obligation (keys,
  certificates, signatures, secure boot, secure communication); an authenticated software-update obligation; a
  data-access or data-retention obligation (data the ECU must store, keep for a period, or expose through an
  interface, e.g. a readable software identification number or stored fault data readable via a diagnostic port); a
  telemetry / transmission obligation (data sent off-vehicle or to a server); an external communication protocol the
  ECU must implement (charging communication, V2G, diagnostic access from outside the vehicle).
- `no`: a new or changed monitoring, warning or control function, an in-vehicle signal (a lamp or tell-tale, a
  signal on the vehicle's internal bus to another in-vehicle controller), a limit, a test, a scope extension, a
  re-approval / transitional date, a hardware requirement.
- **Where I draw the line.** (i) An obligation must be **named**: an option the act merely permits ("may signal
  via ...") is `no` unless the act makes it a required route for some vehicles. (ii) Internal-bus signalling between
  in-vehicle controllers is `no`; transmission to a separate external party (grid, charger, server, external test
  equipment via a standardised interface) is `yes`. A tractor–trailer link that the act makes compulsory is treated
  as external communication (`yes`), since the trailer is a separate vehicle; if only permitted, `no`. (iii) A
  requirement that a value be displayed to the driver is not data access. (iv) Data that must be stored and read out
  (e.g. via OBD or a standard interface) is `yes`.
- `cannot judge`: the text read does not allow the call (e.g. partial-access catalogue entries whose title names a
  subject but not its obligations).
- `stack` is independent of `class`.

### 1.7 `stack_B` rows (L1b §3–§4)

- Rated after all 73 instruments, in `B_events.csv` file order, into `stack_B_A.csv` with columns `act_id`, `domain`,
  `stack`, `confidence`, `note`; `act_id` copied verbatim.
- Each event gets one row `domain = B`, rated for the battery / charging ECU (BMS, OBC, charge communication
  controller, DC-DC, HV energy-data interfaces).
- Each event of a vehicle-level instrument (UN R155, UN R156, GB 44495, GB 44496; B05, B06, B14, B15) gets three rows,
  `B`, `S`, `L`, each rated for that domain's ECU. Since these acts bind every connected or updatable ECU (L-1), an
  obligation the act places on all such ECUs (e.g. secure / authenticated software update, a readable software
  identification) is rated `yes` for each domain; an obligation the act places only on specific functions not
  present in that domain's ECU (e.g. V2X message receivers) is `no` for that domain; scope extensions and
  legacy / transitional relief are `no`.
- Judged from `what_changed`; where that does not allow the call, from the event's source through the allowed
  routes only. No B event is added, removed or re-dated.
